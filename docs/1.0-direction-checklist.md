# Ultimate Line Caller 1.0 Direction And Checklist

Last updated: 2026-08-03

## Purpose

This document captures the current 0.1 prototype app state, the intended 1.0 product
direction, and a milestone checklist that can be updated as features are
implemented.

Use this as the working roadmap for turning the current one-game sideline
prototype into a season-aware, tournament-ready, iPad-friendly line-calling and
stats app.

## Product Direction

Ultimate Line Caller 1.0 should stay fast during live points. The primary game
screen should still make it easy to choose seven players, lock a line, and log
the point result with minimal taps.

Season, tournament, roster, injury, import/export, and analysis features should
support that flow without crowding it. The app should remain local-first and
offline-capable for field use, with explicit backup/export paths so data is not
trapped on one iPad.

## Current 0.1 Prototype State

The app is a compact Vite, React, and TypeScript web app.

- `src/App.tsx` contains the React UI, local component helpers, event handlers,
  modals, and most application flow.
- `src/model.ts` contains shared types, localStorage persistence, game rules,
  line validation, point-context derivation, player counts, and suggested-line
  logic.
- `src/model.test.ts` covers the core model behavior.
- `src/styles.css` contains the full touch-first app layout.
- `index.html` already includes basic iPad web-app metadata.
- `docs/v0.1-prototype/mvp-plan.md`,
  `docs/v0.1-prototype/architecture.md`, and
  `docs/v0.1-prototype/spreadsheet-analysis.md` describe the original
  version 0.1 one-game prototype.

Baseline verification on 2026-08-03:

- `npm test` passed: 12 tests.
- `npm run build` passed.
- Git worktree was clean before this document was added.

Current implemented behavior:

- Create and edit a roster.
- Assign each player as `MMP` or `FMP`.
- Mark players active or inactive.
- Start one active game.
- Configure starting O/D, point-one ratio, target score, and starting field
  side.
- Select a seven-player line.
- Validate line size, ratio, and inactive players.
- Fill a suggested line from lowest point totals.
- Lock a line before logging a point.
- Log whether we scored or the opponent scored.
- Derive score, next point number, next O/D state, required ratio, field side,
  half-time state, and game-over state.
- Track total points played plus O/D points per player.
- Undo the last point.
- Persist the one active game in browser localStorage.
- Show half-time, game-over, and reset confirmations.

Important current limitations:

- The app stores one active game only.
- There is no team, season, tournament, or multi-game model.
- Player `active` is global, not scoped to a tournament or game.
- Deleting a player removes that player from historical point logs, which would
  corrupt season statistics.
- Stats beyond points played, O points, and D points are not tracked.
- There is no roster import/export.
- There is no app backup/restore format.
- There is no CSV export for analysis.
- There is no web manifest, service worker, icon set, offline cache, or
  field-ready install flow yet.
- `package.json` still reports version `0.1.0`; update this when the 1.0 release work begins or when release packaging is formalized.

## 1.0 Design Principles

- Keep line calling fast. Anything not needed during a live point belongs behind
  a drawer, modal, or separate management screen.
- Preserve history. Never delete or rewrite historical game data just because a
  roster changes.
- Prefer scoped availability. A player can be on the season roster, selected
  for a tournament, unavailable for the rest of that tournament, and still
  remain part of long-term team history.
- Store raw events and derive summaries. Point logs and stat events should be
  the source of truth; game, tournament, and season summaries should be derived.
- Stay offline-first. Assume the iPad may have poor connectivity at the field.
- Make backup/export obvious. Local storage is convenient, but not enough by
  itself for valuable season data.
- Avoid a backend until there is a clear need for multi-device sync or shared
  account access.

## Proposed 1.0 Data Model

Add a release-oriented `AppState` with stable IDs and separate entities. The storage schema can still use an internal schema version that migrates from the 0.1 prototype.

```ts
type AppState = {
  schemaVersion: 2;
  teams: Team[];
  activeTeamId: string | null;
  activeSeasonId: string | null;
  activeTournamentId: string | null;
  activeGameId: string | null;
};

type Team = {
  id: string;
  name: string;
  players: Player[];
  seasons: Season[];
};

type Player = {
  id: string;
  name: string;
  genderCategory: "MMP" | "FMP";
  jerseyNumber?: string;
  notes?: string;
  archived: boolean;
};

type Season = {
  id: string;
  name: string;
  teamId: string;
  seasonRosterPlayerIds: string[];
  tournaments: Tournament[];
  createdAt: string;
};

type Tournament = {
  id: string;
  name: string;
  seasonId: string;
  startsAt?: string;
  activeRosterPlayerIds: string[];
  unavailablePlayerIds: string[];
  availabilityEvents: AvailabilityEvent[];
  games: Game[];
};

type Game = {
  id: string;
  tournamentId: string;
  name: string;
  opponent?: string;
  settings: GameSettings;
  pointLog: PointLogEntry[];
  manualHalfTimeTarget: number | null;
  pendingHalfTimeCap: boolean;
  finalized: boolean;
  createdAt: string;
};

type AvailabilityEvent = {
  id: string;
  playerId: string;
  tournamentId: string;
  status: "unavailable" | "available";
  reason?: string;
  createdAt: string;
};

type StatKind = "d" | "score" | "assist" | "throwaway";

type StatEvent = {
  id: string;
  gameId: string;
  pointNumber: number;
  playerId: string;
  kind: StatKind;
  createdAt: string;
};
```

Notes:

- Preserve existing `GameSettings`, `PointLogEntry`, ratio, O/D, side, cap, and
  score derivation logic where possible.
- Keep `StatEvent` separate from `PointLogEntry` so stats can be added or fixed
  after the point without changing who played.
- Treat `Player.archived` as a soft delete. Archived players should not appear
  in new roster pickers by default, but their historical stats remain intact.

Recommended deployment path:

1. Ship 1.0 first as a static HTTPS-hosted PWA.
2. Install it on iPads from Safari using Add to Home Screen / Open as Web App.
3. Keep all data local and offline, with explicit backup/export.
4. Only move to Capacitor/TestFlight if native packaging becomes necessary.
5. Only add backend sync if multi-device shared state becomes necessary.

Deployment notes:

- Apple supports adding websites to the iPad Home Screen.
- Newer Safari/WebKit releases support more capable installed web apps, but
  explicit manifest, icons, and service worker support are still useful.
- Browser storage can be evicted under some conditions, so export/backup cannot
  be optional for valuable season data.
- TestFlight is a good later option for a native wrapper.
- MDM or enterprise distribution is only worth considering for managed team or
  organization-owned iPads.

## Suggested Build Order

1. Model and migration.
2. Component/screen refactor with no behavior change.
3. Season/tournament/game selection.
4. Scoped roster availability and injuries.
5. Roster import/export.
6. Stats event capture.
7. Stats summaries and CSV export.
8. PWA install/offline hardening.
9. iPad field test.

This order keeps risk low: first make the state capable of representing 1.0,
then add management screens, then add live-game features, then harden deployment.
